# Code audit, 2026-09-29

Scope: the whole repository at `81ac178` on `main`. Covers best practice, design, data modeling and SQL. Fixes are planned in `docs/FIX-PLAN.md`, which uses the same IDs.

## Summary

The app is in good shape. No critical or high-severity problem was found, and every item from the three earlier security reports is still closed. The remaining work is structural:

1. History references lanes by name instead of by id. This is why lanes cannot be renamed and why most analytics queries join on text.
2. The most complex logic in the app, the stage-move SQL, has no automated test and there is no CI.
3. The schema has no indexes on its foreign keys and carries two unused tables.
4. There is no development database. `.env.local` points at production, so the dev server, local migration runs, scripts and `npm run reset:db` (which has no confirmation) all act on the real data.

Counts: 8 medium, 23 low.

## Data model

### DB-1 (Medium) History references lanes by name

`application_transitions.from_status` and `to_status` hold lane names as text. There is no foreign key.

- Lanes cannot be renamed (`db.ts:269`, `stage-dialog.tsx:26`). To fix a typo the owner has to create a new lane and move every card.
- Deleting a lane and creating another with the same name silently merges their history.
- Every analytics query joins on `s.name = t.to_status` (`db.ts:192`, `399`, `558`, `849`, `868`, `940`, `958`).
- Nothing stops a row from naming a lane that never existed.

### DB-2 (Medium) Foreign key columns are not indexed

Confirmed on the live database: the only indexes are primary keys and the two unique constraints on `stages`. Postgres does not index foreign keys automatically.

- `application_transitions.application_id` is probed once per application by the correlated subqueries in `listApplications`, `getSankeyData` and five of the stats queries. Each probe is a sequential scan.
- `applications.stage_id` is scanned on every lane delete and every stage count.

Invisible at 35 rows. It grows as applications times transitions.

### DB-3 (Medium) `reset:db` is unguarded and diverges from the migrations

`scripts/reset-neon-db.mjs`:

- Truncates all three tables with no confirmation and no environment check. `.env.local` holds a single `DATABASE_URL`, so on this machine it targets the real data.
- Carries its own copy of the table definitions. That copy lacks the `kind` CHECK constraint and the unique constraint on `sort_order`, and it does not write `schema_migrations`. Run against an empty database it produces a schema the app accepts but the migrations did not build.
- Seeds a fixed lane list that duplicates `DEFAULT_STAGE_NAMES` and the seed in the first migration.

### DB-4 (Low) Unused tables in the live database

`application_transitions_backup` was created by migration `1730000002000` and never dropped; it holds 9 rows, a copy of the history as it was before that migration rewrote it. `pgmigrations` is left over from a previous migration tool and holds 1 row. No code reads either.

### DB-5 (Low) Lane names are unique only case-sensitively

`stages_name_key` is a plain unique constraint, so `Applied` and `applied` can coexist. The reserved-name check, the chart colours and the backfill migrations all compare lowercase.

### DB-6 (Low) Few constraints at the database level

Length limits and non-blank checks exist only in `api-validation.ts`. The database accepts an empty `company`, a negative `sort_order`, or a transition from a lane to itself. Ids use `SERIAL` rather than identity columns.

### DB-7 (Low) History is rewritten, not appended

A backward move deletes rows (`db.ts:587`). That is deliberate and documented, but the original timestamps and the fact that a rewind happened are lost, so questions such as "how often did I undo a rejection" cannot be answered later. Related: there is no creation event, so the entry lane has to be derived in three separate queries.

### DB-8 (Low) Migration hygiene

- Migration `1730000001000` adds `interview_date`, which the first migration already creates. The first migration was edited after it shipped.
- The runner takes no lock, so two concurrent runs can both apply the same migration.
- There are no down migrations. Acceptable for this project, but not written down anywhere.

## SQL and the data layer

### SQL-1 (Medium) The stats page runs 14 independent queries

`getStatsData` (`db.ts:808`) sends 14 statements through `Promise.all`. With the Neon HTTP driver each one is a separate HTTPS request and a separate snapshot.

- A write landing between them produces totals that disagree with each other on the same page.
- `listStages()` and the stage count query fetch the same rows.

`sql.transaction([...], { readOnly: true, isolationLevel: "RepeatableRead" })` would send them as one request with one snapshot.

### SQL-2 (Low) Filters for legacy `created` rows are dead code

Seven predicates of the form `LOWER(from_status) <> LOWER('created')` remain (`db.ts:764`, `835`, `883`, `910`, `918`, `959`), plus `scripts/cleanup-created-transitions.mjs` and its npm script. The live database has no such rows. The `LOWER()` calls would also defeat any index on those columns.

### SQL-3 (Low) The same subqueries are repeated

- "Latest transition into the current lane, else `created_at`" appears four times (`db.ts:189`, `396`, `846`, `937`).
- "Entry lane" appears three times (`db.ts:533`, `768`, `899`).

A definition changed in one place and not the others produces numbers that disagree between the board and the stats page. The earlier report raised this as STD-3 and it is still open.

### SQL-4 (Low) Writes take more round trips than needed

A stage move sends up to four requests: `ensureSchema`, a check that the target lane exists (`db.ts:663`, `718`), the move, and `selectApplicationById`. The existence check is redundant because the foreign key violation is already caught and mapped (`db.ts:636`).

### SQL-5 (Low) Row mapping depends on case folding

Queries alias columns as `AS interviewDate`; Postgres folds that to `interviewdate`, and `mapApplication` reads the folded key (`db.ts:77`). A reader who quotes an alias or adds a column in camelCase gets `undefined` with no type error, because every result is cast from `Record<string, unknown>[]`.

### SQL-6 (Low) Lane kinds are hard-coded in some queries

`WHERE kind = 'active'` (`db.ts:160`), `kind = 'interview'` (`db.ts:868`) and `kind IN ('offer','rejected','closed')` (`db.ts:963`) sit next to queries that use `TERMINAL_KINDS` and `STALE_EXCLUDED_KINDS`. The "resolved" set that includes `offer` is also written out in `stats-charts.tsx:24` and has no name in `stage-kinds.ts`.

### SQL-7 (Low) Upcoming interviews include finished applications

The query at `db.ts:922` has no filter on lane kind. An application moved to Rejected with a future `interview_date` still shows under "Upcoming Interviews".

### SQL-8 (Low) `ensureSchema` checks only part of the schema

It verifies three tables and the `kind` column (`db.ts:89`). It does not notice a missing `stages_sort_order_key`, which `addStage` relies on, or a CHECK constraint that predates the `closed` kind. It also adds a catalog query to every cold start.

### SQL-9 (Low) Small ordering and grouping inconsistencies

- `listApplications` orders by `updated_at` with no tie-breaker, so cards with equal timestamps can swap places between loads.
- "Top companies" groups by exact `company` text, while the duplicate warning in the dialogs compares trimmed lowercase.

## API and architecture

### ARCH-1 (Medium) Guest redaction is applied by each caller

Notes are stripped for guests in two places, `src/app/board/page.tsx:16` and `src/app/api/applications/route.ts:22`. `listApplications()` itself returns notes to anyone. A new endpoint or page that calls it has to remember to redact.

### API-1 (Low) Error modeling is inconsistent

- `deleteStage` returns `{ deleted, reason }` and the route picks the status by comparing the reason string (`stages/[id]/route.ts:35`). Every other function throws a typed error.
- `ApiValidationError` and `ApiError` are separate hierarchies handled by two branches in `errorResponse`.
- Success bodies are `{ success: true }` in some routes and `{ ok: true }` in others.
- `PATCH /api/applications/:id` requires every field, which is `PUT` behaviour.
- `expectedStageId` is mandatory in the routes but optional in the `db.ts` signatures, where `null` disables the concurrency guard.

### API-2 (Low) Logo lookup sits in the request path

`POST /api/applications` waits up to 3 seconds for Clearbit before inserting. The logo is never refreshed when the company name is edited. The endpoint returned 200 during this audit, but it is an unauthenticated third-party service with no guarantee.

### ARCH-2 (Low) Three files hold most of the code

`db.ts` (1070 lines), `kanban-board.tsx` (645) and `stats-charts.tsx` (620). `db.ts` mixes connection setup, row mapping, lane CRUD, application CRUD, the move statement and all analytics.

## Security

No new vulnerability was found. These are residual or hardening items.

### SEC-1 (Low) Login throttle is per instance

Documented in the code (`login/route.ts:17`). On serverless hosting each instance has its own counter and a cold start clears it.

### SEC-2 (Low) Response headers are minimal

`next.config.ts` sets `frame-ancestors`, `nosniff` and a referrer policy. There is no `script-src` or `default-src` policy and no `Permissions-Policy`.

### SEC-3 (Low) Analytics events carry lane names

`trackApplicationMoved`, `trackStageAdded`, `trackApplicationCreated` and `trackApplicationUpdated` send lane names to Vercel Analytics. Lane names are free text typed by the owner.

## Frontend

### UI-1 (Low) No error boundaries

`src/app` has no `error.tsx`, `global-error.tsx` or `not-found.tsx`. A database failure while rendering a page shows the framework's default error screen.

### UI-2 (Low) Moving a card requires a mouse

The board uses native HTML5 drag and drop, which has no touch or keyboard support. The edit dialog can change the lane but opens only on double-click. Errors and confirmations use `alert()` and `confirm()`.

### UI-3 (Low) "Applied" date is the creation date

The card shows `Applied <created_at>` (`kanban-board.tsx:200`) and "days to interview" counts from `created_at`. For a card that started in a Wishlist lane both include the time before the application was sent.

### UI-4 (Low) Relative ages are computed during render

`daysSince()` calls `Date.now()` on the server and again during hydration (`kanban-board.tsx:201`, `573`). The two disagree only when a card crosses an exact 24-hour age mark in the interval between the server render and hydration, so a mismatch is rare. Lowest priority in this group.

### UI-5 (Low) Board refresh fails silently

`refreshBoard()` returns without a message when the request fails (`kanban-board.tsx:282`), including right after a 409 when the board is known to be out of date.

## Tooling and repository

### OPS-1 (Medium) Development and production share one database

`.env.local` holds the production `DATABASE_URL`; there is no separate development database. Consequences:

- `npm run dev` reads and writes live data. Trying out a feature on the board, or an agent clicking through it, changes real applications.
- Migrations are tried for the first time on production. Today's `1730000005000` was checked only inside a rolled-back transaction on the live database, which held an exclusive lock on `stages` for the length of that transaction.
- DB-3 is dangerous mainly because of this. A guard in `reset:db` reduces the risk; a separate database removes it.
- Every test or check that needs Postgres has nowhere safe to run except an in-process database.

### TEST-1 (Medium) The stage-move SQL is untested and there is no CI

`stageMoveQuery` is about 120 lines of data-modifying CTEs. Its correctness is argued by comments that point to a TypeScript twin, and only the twin is tested. The verify scripts are plain `node:assert` files with no shared runner, no `npm test`, and nothing runs them on push.

### DOC-1 (Medium) Documentation had drifted

Addressed in this pass for `CLAUDE.md`, `AGENTS.md` and `README.md`. Still open:

- `ROADMAP.md` lists search, the stats dashboard and stale alerts as future work. All three have shipped.
- `change_audit_report.md`, `claude-security-bug-assessment.md` and `claude-security-reaudit.md` sit in the repository root, total 577 lines, and describe branches that have since merged.

### TOOL-1 (Low) Script and lint gaps

- No `typecheck` script; the command is documented but has to be typed out.
- `sankey-chart.tsx` uses `any` for every Recharts callback and the lint config does not flag it.

### TOOL-2 (Low) Stray local files

`data/jobhunt.sqlite` and its companions remain from the SQLite version of the app. They are ignored by git and unused.

## Things that are done well

Worth keeping as they are:

- Every route handler re-checks the session instead of trusting the proxy.
- The stage move is a single statement with an optimistic concurrency guard, so concurrent moves cannot fork history.
- The unique constraint on `sort_order` is deferrable, which makes bulk renumbering safe.
- Input validation is strict about integer parsing, calendar dates and URL schemes.
- Session tokens are bound to a keyed hash of the credentials, so rotating a password revokes sessions.
- The Sankey graph is built as a DAG by construction, with a second check in the client.
- Migrations run inside real transactions over a WebSocket client, with the reason written down.
- Comments explain why, not what.
